## 2. VM 测试矩阵与 arm64 资源规划（J2、R-TEST-03、ADR-063）

### 2.1 Pairwise（正交）裁剪测试矩阵（避免组合爆炸）

全因子组合（15 OS × 3 架构形态〔`amd64` / `arm64-4K` / `arm64-64K`〕× 3 K8s 版本 × 2 CRI × 4 CNI × 3 拓扑）不可行。**12 组正交 VM 测试矩阵（`M01`–`M12`）以 [`deep-design/G3 §1.1`](./deep-design/G3-平台-多架构测试平台故障注入与500节点压测SOP深度设计.md) 为唯一权威定义**，本节不再重复列表以避免漂移。关键覆盖映射：
- `M01`（Rocky 9 `amd64/4K` 离线 3+3 HA，每日）、`M02`（Rocky 8.10 `glibc 2.28` / `iptables` 降级，每日）、`M03`（Ubuntu 24.04 双栈 + Cilium，每次 PR）、`M04`（Ubuntu 26.04 `sudo-rs` + `uutils`，每日）、`M05`（Debian 13 纯 nftables，每日）；
- `M06`（openEuler 24.03 `arm64/4K`，每日）、`M07`（麒麟 Kylin V10 SP3 `arm64/64K` 每日，符合 `03-A §5` 实测 64K 规则）、`M08`（麒麟 Kylin V11 `arm64/4K` + KYSEC，每日/每周）、`M09`（统信 UOS V25 离线闭包）、`M10`（Anolis 23 `arm64/4K`）、`M11`（openSUSE Leap 16 + SELinux enforcing）、`M12`（混合架构 `3×amd64 + 2×arm64-4K + 1×arm64-64K`）。

### 2.2 VM 编排与 arm64 资源选型（R-TEST-03、ADR-063）

- **VM 编排**：本地宿主机采用 **libvirt / QEMU + cloud-init + Packer（黄金基础镜像）+ Terraform libvirt provider** 自动拉起与销毁隔离测试网段（包含纯断网内部网桥验证离线安装）；不采用 `kind`（`kind` 共用宿主机内核且非 systemd 二进制安装，仅可辅助测 K8s API/Addon，不能替代 VM）。

## 3. OS 命令行为与 `sudo-rs` / `uutils` VM 回归（D5、R-INIT-11）🔬

> **2026-04 关键上游事实**：Ubuntu 26.04 LTS（Resolute Raccoon，2026-04-23 发布，内核 7.0）正式默认使用 **`sudo-rs`（0.2.13）** 与 **`rust-coreutils`（uutils 0.7.0）**（其中 `cp`、`mv`、`rm` 因 TOCTOU 边界暂保留 GNU 实现，但 `ls`、`stat`、`date`、`dd`、`sha256sum`、`chmod`、`chown`、`tee`、`sort`、`tr`、`mktemp` 等均已切换为 Rust 实现）。

**专项回归用例清单（`M-03` 必跑）**：
1. **sudoers 语法与提权（ADR-030）**：验证 Mode A（`NOPASSWD: ALL`）与 Mode B（无参白名单脚本 `""`）在 `sudo-rs` 下解析与执行成功，确认 `sudo -n true` 与 `sudo -S -p ''` 退出码与提示符行为一致，且不触发局部参数通配符报错；
2. **coreutils 标志兼容**：在全部内置 Task 与 Facts 采集脚本中执行一次端到端扫描，验证 `stat -c`、`sha256sum`、`base64 -d`、`date -u`、`mktemp -d`、`chmod`、`chown`、`df -PB1` 输出格式与 GNU 完全一致；
3. **无 Python / 无 bashism 验证**：在仅装 POSIX `dash` + `uutils`、未装 `python3` 的容器与 VM 中跑通 Facts 采集与全量初始化模块（ADR-025）；
4. **回退验证**：确认在异常兼容问题发生时可通过文档指引检测 `sudo -V` 识别 `sudo-rs` 并在报告中明确标注实现类型。

## 4. 商业信创 OS 真机采样与回填规范（R-OS-07、R-OS-19 / 22）🔬

针对无公开官方源的商业 OS（统信 UOS V20 1070a/e、UOS V25、CTyunOS、银河麒麟 V10/V11 特定 SP）：
1. **授权采样流程**：由客户或厂商提供授权 VM/物理机 → 在目标机以只读权限运行仓库自带的只读探测脚本（沿用 `research/probe.py` 思路），采集 `/etc/os-release`、`/etc/*-release`、`uname -r`、`getconf PAGESIZE`、`systemd --version`、`/sys/fs/cgroup` 挂载类型、`rpm -qa` / `dpkg -l` 核心包名、KYSEC/fapolicyd/SELinux 状态，输出脱敏 JSON；
2. **回填 `spec/`**：
   - 将实测 `/etc/os-release` 样本追加至 `spec/osmatch_golden.yaml`（标明 `source: measured` 与日期）；
   - 如有新字段匹配或包名差异，更新 `spec/osmatch.yaml` 与 `spec/pkgmap.yaml`；
   - 运行 `python3 spec/gen_os_docs.py --write && python3 spec/gen_os_docs.py --check` 确认 03 表格与全量 golden/pkgmap 回放 100% 通过后提交 PR。

## 6. 故障注入与高可用演练手册（J5、ADR-064）

所有生产级 K8s 发版前必须在 3 主 3 从集群（`M01`）执行全部 15 项权威故障注入用例（ADR-064，`G3 §3.1` 同编号实现）（工具：`tc netem`、`nft drop`、`stress-ng`、`kill -9`、宿主机强制断电 `virsh destroy`）：

| 编号 | 场景 | 注入方法 | 预期与硬性判定 |
| --- | --- | --- | --- |
| `FI-01～08` | **节点本地代理 8 项故障** | 按 `04 §9.3` 逐项执行（单控制面宕机、端口 hang、半开连接、后端热更新、全部失联恢复等） | 故障摘除 ≤ 5 s，业务 Pod 访 apiserver 无长时间阻塞，热重载零断连 |
| `FI-09` | etcd 单成员宕机 + 磁盘慢 | `virsh destroy` 1 台主节点；另一台用 `tc` / `dm-delay` 注入 30 ms 磁盘 fsync 延迟 | 集群写操作持续可用；延迟超 `04 §10.3` 阈值时 Prometheus 准确触发 `EtcdDiskWalFsyncDurationHigh` 告警 |
| `FI-10` | 控制面 VIP 漂移 | 强杀当前持有 VIP 的控制面节点 | Keepalived / kube-vip ≤ 5 s 漂移至备控制面，集群外 `kubectl get nodes` 恢复 |
| `FI-11` | 运行时 containerd 重启 | 工作节点 `systemctl restart containerd` | 已运行容器不断流（containerd-shim 托管），节点保持 `Ready` |
| `FI-12` | 节点证书到期轮换 | 缩短测试集群 kubelet 证书 TTL 为 10 分钟 | `kubelet-csr-approver` 自动校验 CN/SAN 并审批续期（ADR-017），拒绝伪造 SAN 的恶意 CSR |
| `FI-13` | **部署机中途断连与续装** | 安装第 5 Phase 时 `kill -9 kinstall` 进程 | `kinstall apply --resume <opId>` 跳过已完成且参数摘要一致的 TaskRun，续跑至成功 |
| `FI-14` | **Server 多副本崩溃租约接管** | 2 副本 Server（PG）执行长任务期间 `kill -9` 持有租约副本 | 30 s 租约过期后另一副本抢占接管，先 Check 正在运行的 TaskRun 状态再继续，零重复副作用 |
| `FI-15` | **etcd 灾难恢复演练** | 删除全部 3 台 etcd 数据目录模拟全毁 | 按 `04 §13` 经审批执行 `etcd-restore` 从备份恢复，全部既有 Deployment 与数据找回 |

## 7. 跨版本升级回归方案（J6）

- **必测升级链**：**`1.35.10 → 1.36.6 → 1.37.2`**（及 1.38 GA 后追加 **`→ 1.38.0`**；每步只允许升一个次版本，验证跳级 `1.35 → 1.37` 被 Planner 阻断）；同时覆盖 `containerd 2.2 → 2.3`、`etcd` 补丁升级、`Calico` 小版本升级与 `1.36 → 1.37` 在 SELinux enforcing 节点上的 `SELinuxMount` 卷标签冲突审计（ADR-032）。
- **连续性探针**：升级全过程由独立探针进程以 10 QPS 持续访问集群内 Ingress/Gateway API 与 ClusterIP 服务，同时持续调用 apiserver `GET /api/v1/namespaces`。
- **判定门槛**：升级全程数据面 HTTP 请求成功率 ≥ **99.9%**，控制面 apiserver 不可用窗口累计 ≤ 15 s；全部节点升级后状态 `Ready` 且无残留旧版本二进制软链；同步测试失败注入后控制面单节点回滚与 etcd 快照回退预案。

## 9. 中间件插件通用验收清单

每个中间件插件（`07`–`11`）发版前必过 5 项通用验收（均记录于验收报告）：
1. **离线安装 + 二次幂等**：纯断网环境完成主推荐拓扑安装，连续二次 `apply` 全 `Skipped`；
2. **安全基线**：匿名/弱密码被拒，全链路 TLS 生效，配置文件与密钥权限符合 `06 §1.1`；
3. **高可用切换**：注入主节点故障，在各插件承诺 RTO 内自动切主且无脑裂、按配置达标 RPO；
4. **备份与恢复演练**：写入校验数据集 → 触发 `backup` → 销毁或新建目标实例 → `restore`（含数据库 PITR）→ 逐条校验数据一致性；
5. **监控与升级**：Prometheus 采集指标齐全、人为触发至少 1 条 Critical 告警验证路由通畅、小版本滚动升级业务不中断。
